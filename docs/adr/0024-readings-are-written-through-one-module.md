# 读数的写入只经读数录入模块

一套水电计费系统里,读数是一切账期的唯一来源:入住、抄表、改、撤、换表、退租最终都落成一条读数。
若每条路由各自内联校验并直接写 `readings`,三相求和、日期先后、隔表比较、已收款锁定这四类规则就会
在六个入口各写一遍,示例数据为了绕开表单还会出现第七条不带校验的旁路。

决定:应用层对 `readings` 的写入只经一个读数录入模块,规则与重算都在模块内部完成;模块以外的代码
只描述"要记录哪一种读数",不再拼 SQL、不再自己决定要不要重算。示例数据与 HTTP 路由共用这同一个入口,
因此它是两个真实 adapter 之间的 seam,不是一个假设的抽象。

考虑过的替代方案:各路由保留自己的校验、只把共用的校验函数抽成工具函数。否掉了——工具函数不会
强制新入口调用它,规则仍会随入口数量漂移。
