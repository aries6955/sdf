# 读侧的账期只有一个视图,页面向它取数

## 决定

「某个账期落到多少钱、还欠多少」由 `app/ledger.py` 的 `ledger_view(conn)` 一次算出:
全部租户的逐期应收、冲抵结果、合计,以及可索引的 `by_key`。首页、统计页、台账页、
抄表页、PDF 都从这里取数,不再各自调用 `household_ledger` 逐户循环。

单户详情仍用 `household_ledger`,它与视图共用同一个纯函数 `_settle`,因此两者逐分一致。

同时,读数的「最新一条」「上一条」这类查询收进 `app/reading_index.py`:
`last_of_line` / `last_of_meter` / `readings_on_line` / `predecessors()`。
读侧页面对读数排序不再自己拼 `ORDER BY`。

## 为什么

冲抵本身是对的,错的是它被算了几遍。修复前:

- `totals`、`all_outstanding`、`household_summaries`、`settled_periods`、`all_ledger_rows`
  五个函数形状各异,实现都是「对每户跑一遍 `household_ledger`」;
- 抄表页每行再补两次单行查询(本期应收、上一条读数)。

实测(3 户示例数据 → 13 户):首页 42 → 122 条 SQL,抄表页 91 条,账期数没变而 SQL 条数
跟着租户数线性涨。这些页面本来只是一份同一组数的不同摆法(GLOSSARY「台账」)。
收成一处后,同一组数据:首页 19、抄表页 31、统计页 28、台账页 5。

第二个理由是「上一条读数」有两个不同的问题:同一块表的上一条,与同一条线的上一条。
换表后两者分叉,而修复前靠一句 `WHERE meter_id=? AND reading_date <= ?` 到处重抄,
其中一处还带着「否则会得出一个巨大的负数」的注释 —— 语义没有安放之处。

## 约束

- 冲抵仍从应收与收退款推导,不持久化(ADR-0011)。
- 视图不改变任何页面口径:毛差仍取自同一组筛选条件(ADR-0008 之后的取舍)。
- 视图只读;写入仍只经读数录入(ADR-0024)与收退款登记。
