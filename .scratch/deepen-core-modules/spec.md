## Problem Statement

用户侧没有新功能诉求。问题在维护侧:这套系统的业务规则几乎全部落在 `app/main.py` 一个文件里
(历史改动次数全仓最高),而"一个账期怎么算"、"一条读数能不能录"、"毛差怎么算"这三件核心事实
各自被写了两到三遍。表现是:

- 想确认"补录到中间会不会算错",必须在六个 HTML 表单入口之间来回对照,而不是读一处规则。
- 同一个读数录入规则在入住、抄表、改、撤、换表、退租六处各写一遍,改一处易漏其余五处。
- 示例数据为了绕开 HTTP 表单,把换表与退租又手写了一遍,且不走校验;两条实现会各自漂移。
- 首页与统计页用两条不同路径算"应收",毛差靠两处口径碰巧一致。
- 锁判定("这一期已收款,不许改")为了得到一个日期区间,要跑完整个租户台账。

## Solution

把散在路由里的三件事收成三个深模块,让每个概念只有一个实现、一个 interface:

- **读数录入**:应用层对读数的写入只经它。三相合成、日期先后、隔表逐相比较、已收款锁定、
  写入后的重算都在模块内完成。六个路由因此只剩"要记录哪一种读数"。
- **账期派生**:账期形状只定义一次,`recompute` 与"记一期"都从同一个派生实现出发。
- **台账汇总**:向租户应收、向部门缴出、两者之差三个数字分开定义在一处,首页/统计/导出共用。

再加一个**租期操作**模块承载入住、退租、换表三个归属动作(归属只来自租期),示例数据改为调用它,
于是示例数据与 HTTP 路由成为同一 seam 的两个 adapter。

对用户可见的变化应为零:页面、文案、表单字段、跳转行为都不变。

## User Stories

1. 作为维护者,我想在一次里读到"一条读数能不能录"的全部规则,以便补录逻辑出问题时知道去哪改。
2. 作为维护者,我想让新增的读数入口自动继承已有校验,以便不必记得再加一遍三相求和。
3. 作为维护者,我想让示例数据走与界面相同的写入路径,以便示例能验证真实代码而不是旁路。
4. 作为维护者,我想让"已收款锁定"有一个比完整台账更窄的 interface,以便抄表路径不必跑全量冲抵。
5. 作为维护者,我想让"应收""缴出""毛差"三个数字各有其名,以便加水/电分型时不会只补一半。
6. 作为维护者,我想让账期的定义只存在于一处,以便修改账期语义时不必找出三份重复的字典。
7. 作为维护者,我想让新增一个列表页只写业务 context,以便不必重述分页与提示条的约定。
8. 作为房东/操作者,我想让所有现有页面与文案保持原样,以便这次重构不改变我熟悉的操作。
9. 作为房东,我想让统计页的毛差仍然按水/电分型正确计算,以便只看水时不会减掉电费。
10. 作为维护者,我想让测试可以只跨模块 interface 断言行为,以便重构实现时测试不必跟着改。
11. 作为维护者,我想让路由层的中文提示文案不被移动,以便已有的端到端断言继续有效。
12. 作为维护者,我想让每个动作仍然是一次事务,以便退租这种跨表写入不会只完成一半。
13. 作为维护者,我想让退租只重算一次账期,以便去掉现在"模块算一遍、路由再算一遍"的重复。
14. 作为维护者,我想让示例数据的前置条件显式失败,以便它构造不出状态时报错而不是静默缺块。
15. 作为维护者,我想让每张票独立全绿,以便任何一个 commit 都可以退回。

## Implementation Decisions

四个模块,均在应用层内,无新依赖、无 schema 变更、无路由变化。

- **读数录入模块**。interface 为:`parts_of`(把表单式的分相输入折成合计与三相)、`insert`、
  `change`、`retract`、`editable`。`insert` 以"读数的种类"为参数,依种类选择校验档位;
  `move_in` 比表上末读数,`periodic` 比前后邻接且走已收款锁定,`move_out` 要求开放租期且日期晚于末读数,
  `switch_out`/`switch_base` 是换表内部读数、不触发重算。拒绝时抛出一个携带用户可见中文文案的异常,
  **由路由捕获后原样作为提示条文本**——文案的所有权留在路由层,避免打穿现有断言。
- **账期派生**:账期形状只由一个函数构造;"记一期"改为"重算并确认这一期存在",
  删掉那份与全量派生重复的构造逻辑。读数录入模块内部调用该模块完成重算,路由不再记得"抄表要重算"。
- **租期操作模块**:`move_in`、`check_out`、`swap_meter` 三个动作,接收已折好的读数部分,
  负责建/关租期、改表的接入关系。HTTP 路由与示例数据是两个 adapter。
- **台账汇总模块**:`tenant_due`(向租户应收)、`paid_to_utility`(向部门缴出,按水/电分列)、
  `margin`(两者之差)。`total_paid`(冲抵后的实收)不进此模块,仍归台账模块。
- **已付款区间**:作为台账模块内的一个窄 interface 暴露,供锁定判定使用;它必须与完整台账的逐期冲抵
  结果逐分一致,由一条一致性断言保证。
- **页面模块**:将分页 HTML、提示条整理、带提示跳转收成两个动作。模板中现有的 `page`/`pages`/`pager`
  名字不变。此项最后做,逐页迁移。
- 示例数据:删除手写的换表、退租、开线、抄表四个平行实现,只保留常量表与对上面模块的调用;
  若它构造不出某个历史状态,应显式报错。

## Testing Decisions

- 好测试的标准:只断言通过 interface 可观察到的行为,不查库表、不依赖实现结构;实现重写后测试应原样通过。
- **新测试写在模块 interface 上**:读数录入的四种拒绝(三相缺相、读数倒退、日期撞位、已收款锁定)
  与三种放行;台账汇总的 `margin == tenant_due - paid_to_utility`;已付款区间与完整台账的一致性。
- 票 05 例外:它是在示例数据里发现的一个真 bug——三相电表在退租与换表两处只写了合计、
  没有分相数值,逐相展示会露馅。它的测试落在示例数据一键填充后逐相数值齐全上,
  并顺带把“三相表的分相读数必须处处齐全”写进读数录入模块的约定。
- **现有测试一条不改**:`tests/` 现有五个文件全部走 HTTP 契约或直接调 `household_ledger`
  (后者是仓库已有的先例,新模块测试沿用),前者断言页面文案与表单跳转。两者都不受影响。
- 每张票完成后跑仓库自己的检查命令(ruff + pytest)全过;不引入新测试框架。
- 不做像素级 UI 回归:视图层只搬代码不改输出,现有 HTML 断言足以覆盖。

## Out of Scope

- 任何用户可见的新功能、新页面、新字段。
- schema 变更与数据迁移(现有表结构已足以支撑)。
- 性能优化本身。已付款区间一项只是顺带把抄表路径的复杂度降下来,不设性能指标、不做压测。
- 认证、密码、示例数据的业务内容。
- 计费与账务规则的任何语义改动:ADR-0011 至 ADR-0023 全部保持不变。
- 模板结构重写与样式调整(DESIGN.md 的组件配方不动)。

## 双轴审查结论(2026-11-19)

Standards 轴与 Spec 轴各由独立子代理完成,结论均为 OK with notes,无 P0。已按 findings 修正:

- **Spec 轴 (c) 真回归**:毛差原应跟随租户与计量线筛选,重构后却按全量相减。改为 `margin_from(应收, 缴出)`,
  两者都取同一组筛选值;`tenant_due` 补 `household_id`。新增断言覆盖按租户筛选的情形。
- **Standards 轴**:`tenancy.check_out` 的无用形参 `household_id` 删除;`tenancy.move_in` 改为返回新建的线号,
  示例数据不再用"取该租户最后一条线"来猜。
- 未采纳:把 `_int`/`_float`、"最后一条读数"SQL 各自收敛为一处 —— 前者是两行纯函数、后者各处查询条件与用途不同,
  合并会把无关的读取耦合起来。`tenancy.meter()` 保留,它是换表路由读表的入口。
